# M0 데이터 출처 리서치 (M0)

> 브랜치: `docs/m0-source-research` · 작성: planner · 상태: PM 승인 (2026-10-08)
> 기준: `CLAUDE.md`, `docs/product-brief.md` (6절 미디어 원칙, 7절 출처 후보, 12절 데모 입력, 13절 PM 결정 대기 목록), `docs/roadmap.md`

## 목표

제품 정의서 7절의 후보 출처마다 **무엇을, 어떤 방법과 조건으로 주는지**를 공식 문서 근거와 확신도로 밝힌다. 그 결과로

1. 영역별 1순위 출처와 대안을 고르고,
2. 필요한 API 키 목록(환경변수 이름 제안 포함)을 만들고,
3. 제품 정의서의 가정 중 맞는 것과 뒤집힌 것을 가리고,
4. 13절 결정 항목마다 선택지와 추천안을 PM에게 올린다.

M0가 끝나면 M1 이후 구현 작업은 이 문서들에서 확신도가 "확인됨"인 출처만 쓴다(`CLAUDE.md` 7절 2항).

## 범위 밖

- 제품 코드, 설정 파일, `.env.example` 작성 (환경변수 이름은 `summary.md` 에 제안만 한다. 추가는 M1에서 backend-dev가 한다)
- 서비스 가입, 로그인, 약관 동의, API 키 발급·사용 (키가 필요한 호출은 PM이 실행할 명령으로만 적는다)
- 미디어 파일 내려받기와 저장소 반입, API 응답 원문 커밋
- `data/` 큐레이션 (M2a, M5에서 content-curator가 한다)
- 기술 스택 비교 자체 (스택에 영향을 주는 발견만 `summary.md` 8절에 적는다)
- 제품 정의서 10절 아이디어 보관함(날씨, 노래·영화 등) 출처 조사
- 해외 장소용 출처
- 법률 판단 (약관 해석이 애매하면 원문 위치와 함께 PM 결정으로 올린다)

## 사용할 외부 출처

이 기능은 출처를 검증하는 일 자체라서, 시작 시점에는 모든 후보가 "미확인"이다. 구현 작업이 아니므로 "확인됨만 쓴다" 규칙은 이 기능의 작업 진행을 막지 않는다.

| 영역 | 후보 (제품 정의서 7절) | 현재 확신도 | 담당 작업 |
|---|---|---|---|
| 장소 검색·좌표 | 카카오 로컬 API, 네이버 지도(NCP) Geocoding, Google Places / Geocoding | 미확인 | T1 |
| 과거 항공사진 | 국토지리정보원 국토정보플랫폼, 브이월드 | 미확인 | T2 |
| 현재 위성·로드뷰 | 카카오맵 로드뷰, 네이버 거리뷰, Google Street View / Maps Static | 미확인 | T3 |
| 기록 사진·영상 | 국가기록원, 서울역사아카이브, e영상역사관(KTV·대한뉴스), 공공데이터포털, 한국관광공사 TourAPI | 미확인 | T4 |
| 그날의 사건 | Wikimedia "On this day", Wikidata, 위키백과 날짜 문서, Wikimedia Commons | 미확인 | T5 |
| 국내 사건 보강 | 국가기록원 기록물, 대한뉴스 회차 목록 | 미확인 | T5 (아래 판단 근거) |

후보 밖에서 더 나은 출처를 찾으면 영역마다 **최대 3개**까지 "추가 후보"로 카드를 쓴다(조사 범위가 끝없이 넓어지는 것을 막기 위함). 영역별로 보면 좋을 추가 후보 예시는 작업별 기준에 적었다. 예시일 뿐 의무는 아니다.

### 국내 사건 보강을 T5에 넣은 이유

선택지는 (a) T4 기록 사진·영상에 합치기, (b) T5 그날의 사건에 합치기, (c) 별도 작업 세 가지였다. **(b)를 택하고, T5가 T4에 의존하게 했다.**

1. **쓰는 곳이 같다**: 국내 사건 보강의 결과물은 "그날의 사건" 섹션(M3, 조건부 M3c)에서 쓰인다. 사건 데이터의 1순위를 고를 때 Wikimedia 계열과 국내 출처를 한 문서에서 비교해야 판단이 쉽다.
2. **묻는 질문이 다르다**: T4는 같은 기관(국가기록원, e영상역사관)을 "장소·연도로 사진을 찾을 수 있나"로 보고, 국내 사건 보강은 "정확한 날짜로 조회할 수 있나"로 본다. 같은 문서에 두 축을 섞으면 7절 질문별 답이 흐려진다.
3. **중복 없이 작업 크기를 맞춘다**: T4는 출처가 5개로 이미 가장 크다. T5는 Wikimedia 계열이라 공개 엔드포인트로 빨리 확인된다. 그래서 T5에 넣되, 접근 방법·인증·라이선스는 T4 출처 카드를 링크로 참조하고 **날짜축 질문만 새로 답한다**.
4. **별도 작업(c)은 과하다**: 출처 2개, 질문 1개짜리 작업은 한 에이전트의 일 단위로 작고, 같은 기관 문서를 세 번째로 다시 읽게 된다.

## 확신도 기준 (모든 리서치 문서 공통)

| 등급 | 정의 | 필요한 근거 | 구현에 쓸 수 있나 |
|---|---|---|---|
| **확인됨** | 공식 1차 출처에서 직접 읽어 확인했고, 현재 유효한 내용이다 | 주장 옆에 공식 문서 URL과 확인 일자(YYYY-MM-DD). 인증 없는 공개 엔드포인트라면 실제 샘플 응답(요청 URL, 확인 일자, 확인한 필드) | 예 |
| **부분 확인** | 공식 근거가 일부만 있다. 또는 문서가 애매하거나 작성·개정 시점을 알 수 없다. 또는 키가 필요해 실제 응답을 확인하지 못했다 | 확인된 부분의 URL, **빠진 부분이 무엇인지**, 확인됨으로 올리는 방법 | 아니오 (확인됨으로 올린 뒤에) |
| **미확인** | 공식 근거를 찾지 못했다. 2차 출처만 있다 | 어디를 찾아봤는지 기록 | 아니오 |

용어와 규칙:

- **공식 1차 출처**: 제공 기관 도메인의 개발자 문서, API 명세, 이용약관, 운영정책, 공지, 공공데이터포털의 해당 데이터셋 페이지, 자료 페이지에 붙은 라이선스 표시(공공누리 마크, CC 표시 포함). 같은 내용이 한국어·영어 문서에서 다르면 둘 다 적고 한국 서비스에 적용되는 문서를 우선한다.
- **2차 출처**: 블로그, 커뮤니티, 뉴스 기사, 다른 회사의 해설, AI 요약. 단서로만 쓰고 근거로 쓰지 않는다.
- **항목별로 매긴다**: 출처 카드의 각 항목(접근 방법, 쿼터, 캐싱·저장 등)에 확신도를 따로 매긴다.
- **종합 확신도 = 필수 항목 중 가장 낮은 등급**. 필수 항목은 `접근 방법`, `커버리지`, `캐싱·저장`, `출처 표시`, `상업 이용`, 그리고 미디어를 주는 출처라면 `변경 허용` 까지. 쿼터와 인증 절차는 필수가 아니지만 반드시 적는다.
- **키 때문에 못 본 경우**: `부분 확인 (PM 호출 대기)` 로 쓰고 6절에 PM이 실행할 명령을 적는다. PM이 결과를 넘겨주면 data-researcher가 새 커밋으로 등급을 올린다.
- **약관 해석이 애매한 경우**: 그 항목은 `부분 확인` 으로 두고, 원문 조항 위치(문서 URL + 조·항 번호나 제목)와 함께 10절 "PM 결정 필요"에 올린다. 해석을 확정하지 않는다.
- 모든 문서 머리에 "이 문서의 약관 해석은 법률 자문이 아니다" 를 적는다.
- 원문 인용은 한 문장 이내, 나머지는 요약한다.

### PM 확인 명령 작성 규칙 (6절)

- 엔드포인트, 헤더 이름, 파라미터는 **공식 문서에서 확인한 것만** 쓰고, 그 문서 링크를 명령 바로 위에 단다.
- 키는 명령에 직접 쓰지 않고 `$ENV_VAR` 로만 쓴다. 이름은 아래 환경변수 이름 규칙을 따른다.
- 헤더가 출력되는 옵션(`curl -v` 등)은 쓰지 않는다. 출력은 `| head -c 3000` 처럼 잘라서 받는다.
- 명령마다 "응답에서 확인할 것"(필드 이름과 기대값)을 적는다.
- 쿼리는 제품 정의서 12절 데모 입력의 장소만 쓴다. T1의 동명 후보 확인처럼 꼭 필요할 때만 4절 예시 장소를 장소만으로 쓴다(생년월일은 쓰지 않는다). 이 예외는 PM이 승인했다(2026-10-08, 아래 "승인 때 PM이 정할 것" 1번).
- 응답 원문은 저장소에 커밋하지 않는다(약관상 저장 허용 여부가 확인되기 전이므로).

형식 예시 (엔드포인트와 헤더는 자리표시. 실제 값은 공식 문서에서 확인해 적는다):

```bash
# 근거: <공식 문서 URL>
curl -sS -G "<공식 엔드포인트>" \
  -H "<공식 문서가 정한 인증 헤더>: $KAKAO_REST_API_KEY" \
  --data-urlencode "query=서울대학교병원" | head -c 3000
# 응답에서 확인할 것: 첫 후보의 이름·주소·카테고리 필드, 좌표 필드와 좌표계
```

### 환경변수 이름 규칙 (T6에서 제안할 때)

- 대문자 스네이크: `<제공자>_<용도>_KEY` 또는 `<제공자>_CLIENT_ID` / `<제공자>_CLIENT_SECRET`. 예: `KAKAO_REST_API_KEY`, `VWORLD_API_KEY`, `DATA_GO_KR_SERVICE_KEY`
- 서버 전용 키는 `VITE_` 로 시작하면 안 된다(Vite는 `VITE_` 로 시작하는 변수만 프론트엔드 번들에 넣는다).
- 약관상 브라우저 키가 꼭 필요한 경우(지도 SDK 등, 제품 정의서 8절 예외)만 `VITE_` 를 붙이고, 도메인 제한 방법을 함께 적는다. 예: `VITE_KAKAO_JS_KEY`
- 키가 없어도 식별 정보가 필요한 출처(예: User-Agent에 연락처를 요구하는 API)는 그 값도 환경변수로 제안한다.

### T1 작업별 기준 — 장소 검색·좌표

2절에 아래 질문이 출처별로 모두 있어야 한다.

1. **병원 이름 검색 정확도**: "서울대학교병원" 의 첫 후보 이름·주소·카테고리를 얻을 수 있는가 (문서·공개 예시로 판단, 실제 결과는 PM 명령).
2. **동 이름 검색**: "광주 서구 풍암동" 이 동 단위로 해석되고, 시·도 / 시·군·구 / 읍·면·동 계층과 코드(법정동·행정동 구분 포함)를 받는가.
3. **광역 지역**: "서울" 이 하나의 가게·건물이 아니라 지역으로 해석되는가.
4. **유형 분류 근거**: 응답의 어떤 필드(카테고리 코드, 주소 계층 필드 등, 필드 이름 명시)로 `REGION` / `NEIGHBORHOOD` / `SPOT` 을 나눌 수 있는가.
5. **동명 후보**: 제품 정의서 4절의 예("중앙병원")처럼 후보가 여러 개일 때 목록으로 받는가, 한 번에 몇 개까지 받는가.
6. **쿼터**: 무료 한도, 초과 시 동작(에러·과금).
7. **약관**: 검색 결과의 저장·캐싱 허용 여부와 기간, 자사 지도 위에 표시해야 하는 의무, 출처 표시, 상업 이용.
8. **좌표계**: 응답 좌표계와 변환 필요성.
9. **대한민국 밖 판정**: 국외 장소를 구별할 수 있는가.
10. **폐업·개명 장소**: 문서에서 확인되는 범위의 처리 방식 (제품 정의서 4절 "찾지 못하는 장소" 안내와 연결).

추가 기준:
- 4절 미디어 매핑은 장소 검색이 미디어를 주지 않으므로 6.2절 중 `lat`·`lng`·`place_ref` 행만 채우고, 나머지는 `해당 없음`. 대신 4절 아래에 장소 결과 매핑 표(`type`, `name`, `address`, `lat`, `lng`, 시·도/시·군·구/동 코드)를 둔다.
- 5절은 날짜와 무관하므로 장소 3개("서울", "광주 서구 풍암동", "서울대학교병원")에 대해 출처별 예상 유형·좌표·후보 수를 판단한다.
- 6절에 카카오·네이버·구글 각각 데모 장소 3개를 조회하는 명령이 있다.
- 추가 후보 예시: 행정안전부 도로명주소 API, 법정동 코드 자료(공공데이터포털). `data/regions.json` 별칭·코드의 원천으로 쓸 수 있는지와 이용 조건을 본다.
- 7절에 "지도·로드뷰 제공자와 같은 회사로 묶을 때"의 장단점을 한 단락 적고 T3에서 이어받는다고 표시한다.

### T2 작업별 기준 — 과거 항공사진

2절에 아래 질문이 출처별로 모두 있어야 한다.

1. **받는 방법**: 좌표와 연도로 항공사진을 받을 수 있는가. API / WMS·WMTS 타일 / 파일 다운로드(신청 절차, 유료 여부, 소요 기간) / 웹 열람만 중 무엇인가.
2. **자동화 허용**: 서버가 프로그램으로 호출하는 것이 허용되는가, 사람의 열람만 허용되는가.
3. **연도 커버리지**: 전국 / 서울 / 광주 각각 촬영 연도 목록이나 범위, 촬영 주기.
4. **촬영일 정밀도**: 메타데이터에 촬영 일자가 있는가, 연도만 있는가.
5. **정렬 가능성**: 정사영상(정사보정)인가, 좌표 참조 정보가 있는가. 현재 위성 이미지와 같은 범위로 겹쳐 비교 슬라이더를 만들 수 있는가.
6. **이용 조건**: 공공누리 유형, 화면 표시, 서버 저장·캐싱, 재배포, 상업 이용, 변경(크롭·리사이즈·겹치기) 허용.
7. **보안 처리**: 가림 처리 구역이 있는가, 데모 지점에 영향이 있는가.
8. **쿼터·요금·키**.

추가 기준:
- 5절: "서울대학교병원"(1995)과 "광주 서구 풍암동"(2002) 각각 출처별로 출생 연도와 같은 해, ±5년 안에서 쓸 수 있는 가장 가까운 촬영 연도를 판단한다. "서울"(1988)은 `REGION` 이라 제품 정의서 5절상 항공사진 비교가 없으므로 `해당 없음` 으로 쓰되 서울 커버리지는 참고로 적는다.
- 1절과 9절에 결론을 쓴다: **7절의 가정("동네 섹션의 핵심은 출생 연도 근처 항공사진과 지금 모습의 비교")이 성립 / 조건부 성립 / 불성립** 중 무엇인지. 불성립이나 조건부면 대안 2개 이상(예: 라이선스가 허용하면 데모 지점만 미리 골라 두기, 슬라이더 대신 원문 링크 + 현재 위성).
- 9절에 6.1절의 근접 연도 초안 ±5년이 촬영 주기에 비춰 적절한지 판단한다.
- 추가 후보 예시: 지자체 항공사진 서비스(서울시, 광주시 등).

### T3 작업별 기준 — 현재 위성·로드뷰

2절에 아래 질문이 출처별로 모두 있어야 한다.

1. **웹 임베드 방법**: JS SDK / iframe / 정적 이미지 URL 중 무엇이 되는가, React 단일 페이지 앱에서 쓸 수 있는가.
2. **과거 시점 로드뷰**: API로 과거 촬영분을 고를 수 있는가.
3. **촬영일 메타데이터**: 로드뷰·위성 이미지의 촬영 시점을 받을 수 있는가 (`captured_at`, "현재 모습" 표기의 근거).
4. **캐싱·저장**: 이미지·타일·스크린샷 저장 금지 조항과 범위.
5. **출처 표시**: 로고·저작권 문구를 가리지 않아야 하는 의무.
6. **다른 이미지와 함께 표시**: 과거 항공사진을 겹치거나 나란히 놓는 비교 슬라이더가 약관상 허용되는가.
7. **키 노출**: 브라우저 키가 필요한가, 도메인 제한 방법, 로컬 개발(`localhost`) 허용 여부 (제품 정의서 8절 예외).
8. **요금·무료 한도**.
9. **한국 내 커버리지 제한**: 한국에서 위성·로드뷰 제공 범위에 제한이 있는가.
10. **상업 이용**과 공개 배포 시 추가 조건(도메인 등록 등).

추가 기준:
- 4절: 저장이 금지되면 `url`·`thumbnail_url` 을 어떻게 채우는지(예: SDK 파라미터로 대체, 저장하지 않음) 명시하고, `license` 는 `provider-terms`, `date_precision` 은 `current` 를 쓸 수 있는지 근거와 함께 적는다.
- 5절: "서울대학교병원"(1995) 좌표에서 로드뷰가 있을지 판단하는 방법(공개 메타 엔드포인트가 있으면 그것, 없으면 PM 명령), "광주 서구 풍암동"(2002) 현재 위성, "서울"(1988)은 `해당 없음`.
- 7절에 두 표를 둔다.
  - **제공자 비교표** (13절 "지도·로드뷰 제공자" 입력): 카카오 / 네이버 / 구글 × 장소 검색(T1 결과 인용), 위성, 로드뷰, 브라우저 키, 비용, 약관 제약.
  - **그때/지금 슬라이더 조합 후보** 1~2개: 과거 = T2의 어떤 출처, 현재 = 어떤 출처, 약관상 성립 여부와 근거.
- 추가 후보 예시: 브이월드 영상지도(현재 영상, 과거 항공사진과 같은 좌표 체계일 가능성).

1. **검색 API 유무**: 자체 API, 공공데이터포털 등록 API, 웹 검색만 중 무엇인가.
2. **날짜 메타데이터**: 촬영일·생산일 필드가 있는가, 정밀도(일/월/연/불명).
3. **장소 메타데이터**: 자유 텍스트 / 행정구역 / 좌표 중 무엇인가.
4. **공공누리 유형**: 자료마다 다른가, 컬렉션 단위인가. 응답이나 자료 페이지에 라이선스 필드가 있는가.
5. **영상 임베드**: 플레이어 iframe 제공 / 원본 핫링크 / 다운로드만 / 불가. 짧은 구간 재생이 가능한가.
6. **이미지 직접 표시**: 썸네일·원본을 우리 화면에 직접 띄우는 것(핫링크)이 허용되는가.
7. **쿼터·키**.
8. **상업·비상업 시나리오**: 각각에서 `embed` 할 수 있는 자료 범위.

추가 기준:

### T5 작업별 기준 — 그날의 사건 + 국내 사건 보강

2절에 아래 질문이 출처별로 모두 있어야 한다.

1. **연·월·일 정확성**: 응답에서 연도까지 맞춰 정확히 그날의 사건만 거를 수 있는가. 데모 날짜 3개(1988-09-17, 2002-06-22, 1995-03-15) 각각 그 해 사건이 몇 건인가.
2. **한국어 데이터 양**: 한국어와 영어 응답의 사건 수 비교.
3. **12절 기대 사건**: 1988-09-17 서울 올림픽 개막이 어느 출처에서 나오는가. 나머지 두 날짜에서 나오는 국내 사건이 있는가 (예: 2002 월드컵 기간의 경기).
4. **이미지 라이선스 메타데이터**: Commons에서 라이선스·작가·촬영일을 어떤 필드로 받는가. 사건 대표 이미지가 비자유(공정 이용) 이미지일 수 있는가, 걸러낼 방법이 있는가.
5. **텍스트 재사용 조건**: 사건 요약 문장을 화면에 쓸 때의 라이선스와 출처 표시 방식.
6. **`tone` 판정 근거**: 참사·전쟁·테러를 구별할 구조화된 데이터(예: Wikidata 분류)가 있는가. 판정 방식 후보 2~3개(규칙 / 큐레이션 목록 / 혼합)와 각각의 한계 (제품 정의서 6.3절).
7. **이용 정책**: User-Agent 요구, 호출 속도 제한, 캐싱 허용, 엔드포인트의 현행 여부와 지원 중단 공지.
8. **국내 사건 보강**: 국가기록원 기록물을 생산일자로 조회할 수 있는가, 대한뉴스 회차 목록의 방영일과 수록 기간. 데모 날짜 3개 각각 해당 회차·기록이 있을 가능성. 정밀도가 6.1절 표기(같은 날/같은 달/같은 해/±N년)와 맞는지, 맞지 않으면(예: 주간 단위) 9절에 적는다.

추가 기준:
- **실제 응답 확인**: 인증 없는 공개 엔드포인트(On this day 한국어·영어, Wikidata 질의, Commons 이미지 메타데이터)는 데모 날짜 3개로 실제 WebFetch하고, 카드의 `샘플 응답 확인` 에 요청 URL, 확인 일자, 확인한 필드, 그 해 사건 수를 적는다.

- 4절 아래에 **사건 레코드 필드 제안**(예: `date`, `title`, `summary`, `tone`, `source_name`, `source_url`, `license`, `media[]`)을 둔다. M3 계획서의 입력이며 확정이 아니다.
- 7절에 "국내 사건 보강을 MVP(M3c)에 넣을 가치" 판단을 적는다.

## 6. PM 결정 목록

| 단계 | 이 기능에서 하는 일 |
|---|---|
| 1단계 계획 ⏸ | PM 승인 후 오케스트레이터가 `main` 에서 `docs/m0-source-research` 를 만들고 이 계획서와 `docs/roadmap.md` 를 커밋 (`docs(plan): ...`, `Agent: planner`) |

### 리뷰에서 확인할 것 (code-reviewer)

1. 공통 완료 기준 C1~C13과 T6 기준 S1~S10의 "확인 방법" 명령과 대조를 실제로 돌린다.
2. **근거 링크 직접 확인**: 영역 문서 5개마다 최소 1개씩, 전체 최소 5개의 "확인됨" 주장을 WebFetch로 열어 근거와 맞는지 확인한다. 약관 항목(캐싱·저장, 상업 이용, 출처 표시)을 우선 고른다. 결과는 보고서의 "근거 링크 직접 확인"에 주장별로 적는다.
3. "미확인"이나 "부분 확인"이어야 할 것을 "확인됨"으로 쓴 것, 2차 출처를 근거로 쓴 것, 근거 없는 약관 해석은 **필수** 지적이다.
4. 카드의 종합 확신도가 필수 항목 중 가장 낮은 등급과 같은지 확인한다.
5. `summary.md` 에 영역 문서에 없는 새 사실이 있는지 확인한다.
6. 문서 안에 키 값이 없는지, 생년월일 예시로 데모 입력(12절) 외의 날짜를 쓴 곳이 없는지 확인한다. (촬영 연도, 수록 기간 같은 출처 정보의 날짜는 해당 없음)
7. 브랜치의 data-researcher 커밋이 `docs/research/` 밖을 바꾸지 않았는지 확인한다.
8. 같은 작업이 2번 연속 리뷰를 통과하지 못하면 `CLAUDE.md` 2절 4단계대로 PM에게 넘긴다.
