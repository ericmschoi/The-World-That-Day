## 마일스톤 상세

### M0 데이터 출처 리서치 — `docs/m0-source-research`
- 목표: 제품 정의서 7절의 후보 출처마다 접근 방법, 커버리지, 쿼터, 약관을 공식 문서 근거와 확신도로 정리하고, 구현에 쓸 1순위 출처를 고른다.
- 포함 범위: 영역 5개(장소 검색·좌표, 과거 항공사진, 현재 위성·로드뷰, 기록 사진·영상, 그날의 사건 + 국내 사건 보강) 리서치 문서와 `docs/research/summary.md`.
- 의존: 없음.
- 완료 기준 요약: 영역 문서 5개 + 요약 1개가 계획서의 공통 템플릿과 확신도 기준을 따르고, 데모 입력 3개에 대한 영역별 판단과 13절 결정 항목별 선택지·추천안이 있다. code-reviewer가 근거 링크를 직접 열어 확인하고 승인한다.
- 계획서: `docs/plans/m0-source-research.md`

### M1 부트스트랩 — 2개로 나눈다
- 나누는 이유: Gradle·Spring 설정, Docker Compose, Flyway, CI와 Vite·React·테스트 도구 설정을 합치면 직접 쓰는 코드와 설정이 400줄을 넘을 가능성이 크다. 폴더도 `server/` 와 `web/` 로 깨끗이 나뉜다.
- M1a `chore/bootstrap-server` (backend-dev)
  - 범위: `server/` Gradle 프로젝트(`the-world-that-day`, 패키지 `io.github.ericmschoi.theworldthatday`), Docker Compose의 PostgreSQL, Flyway 기준 마이그레이션, 헬스 체크 API, Testcontainers 스모크 테스트, `.env.example`, CI 서버 잡(테스트·린트).
  - 완료 기준 요약: `docker compose up -d db` 후 `cd server && ./gradlew test` 통과, 헬스 체크가 200, PR에서 CI 서버 잡 통과.
- M1b `chore/bootstrap-web` (frontend-dev)
  - 범위: `web/` Vite + React + TypeScript, Vitest·Testing Library·MSW, 린트·포맷, 입력 화면 자리와 빈 결과 화면(오프닝·동네·도시·세계·마무리 섹션 자리), 개발 서버 프록시, CI 웹 잡.
  - 완료 기준 요약: `cd web && npm test` 와 린트 통과, 빈 결과 화면에 섹션 자리 5개가 보이는 컴포넌트 테스트, CI 웹 잡 통과.
- M0 이후 확정: 기술 스택 세부(지도 SDK 사용 여부, 좌표 변환 라이브러리 필요 여부), 배포 여부에 따른 CI 범위(13절 "배포 여부와 대상").

### M2 장소 해석과 입력 — 2개로 나눈다
- 바꾼 점: 제품 정의서 11절의 M2(장소 해석)에 입력 화면의 날짜 검증과 **오프닝**(5절 1번)을 붙였다. 오프닝은 검증된 날짜와 해석된 장소 이름이 있어야 만들 수 있고, 이후 모든 섹션이 붙을 결과 화면의 뼈대가 되기 때문이다.
- M2a `feat/place-resolve` (content-curator + backend-dev)
  - 범위: `data/regions.json`(시·도/시·군·구 별칭과 코드), 장소 검색 어댑터(M0 1순위), 유형 분류, 후보 목록, 대한민국 밖·찾지 못함 응답, 약관이 허용하면 캐시.
  - 완료 기준 요약: 녹화한 fixture로 "서울" → `REGION`, "광주 서구 풍암동" → `NEIGHBORHOOD`, "서울대학교병원" → `SPOT` 과 좌표를 반환하는 테스트 통과.
- M2b `feat/input-and-opening` (backend-dev + frontend-dev)
  - 범위: 날짜 검증(미래, 존재하지 않는 날짜, 지원 시작 연도), 후보 선택 UI, 찾지 못함·해외 안내, 오프닝("1988년 9월 17일 토요일, 서울").
  - 완료 기준 요약: 데모 입력 3개의 오프닝 문구와 요일이 맞고, 잘못된 날짜가 거부되는 테스트 통과.
- API 형태: 섹션별 엔드포인트(예: `/api/places/resolve`, `/api/story/world`, `/api/story/neighborhood`)로 나누어 늦게 오는 섹션을 나중에 채우는 방식을 권장한다. M2 계획서에서 확정한다.
- M0 이후 확정: 장소 검색 제공자(13절 "지도·로드뷰 제공자"와 같은 회사로 묶을지), 지원 시작 연도(13절).
- M2 계획 때 PM이 정할 것: 지도에서 직접 위치를 고르는 기능을 넣을지(제품 정의서 4절).

### M3 그날의 세계 — 2개 + 조건부 1개
- 나누는 이유: 사건 어댑터·정확한 날짜 필터·Commons 라이선스 해석·`tone` 판정(백엔드)과 섹션 UI·미디어 캡션·`link_only` 렌더링(프론트엔드)을 합치면 400줄을 넘는다.
- M3a `feat/world-events-api` (backend-dev): 사건 출처 어댑터, 같은 연·월·일 필터, 미디어 레코드(6.2절 필드 전부)와 `date_precision` 계산, `display_mode` 결정, `tone`. 여기서 **공용 미디어 형식**(`data/schema/media.schema.json` 과 API DTO)을 확정한다. M4·M5가 재사용한다.
- M3b `feat/world-events-ui` (frontend-dev): 그날의 세계 섹션, `tragic` 사건 분리 표시, 공용 미디어 카드(출처·라이선스·촬영 시점·정밀도 표시, `link_only` 는 썸네일 없이 링크).
- M3c `feat/domestic-events` (조건부): 국내 사건 보강. M0의 `docs/research/day-events.md` 결론과 PM 결정에 따라 넣거나 뺀다.
- 완료 기준 요약: 1988-09-17 결과에 서울 올림픽 개막이 나오고(제품 정의서 12절), 라이선스가 확인되지 않은 미디어는 `link_only`, 모든 미디어에 정밀도 표기가 있다.
- M0 이후 확정: 사건 출처 1순위, `tone` 판정 방식, 영상 처리 방식(13절), 상업 이용 여부(13절).

### M4 그날의 동네 — 3개로 나눈다
- 나누는 이유: 항공사진, 로드뷰, 동네 사진은 출처와 약관이 각각 달라 따로 리뷰하는 편이 안전하고, 합치면 400줄을 크게 넘는다.
- M4a `feat/aerial-compare`: 항공사진 어댑터, 출생 연도에 가장 가까운 촬영 연도 선택, 현재 위성 레이어, 그때/지금 비교 슬라이더. 계획 단계에서 400줄을 넘을 것 같으면 API와 UI로 다시 나눈다.
- M4b `feat/streetview`: `SPOT` 로드뷰 임베드(브라우저 키는 도메인 제한), 촬영 시점 표시.
- M4c `feat/neighborhood-photos`: 동네 곳곳 3~6장.
- 완료 기준 요약: "광주 서구 풍암동"(2002)과 "서울대학교병원"(1995)에서 비교 슬라이더가 촬영 연도와 "현재 모습" 표기와 함께 나오고, 로드뷰가 `SPOT` 에서만 나오며, 지도 제공자 약관(캐싱 금지, 로고 표시)을 지킨다.
- M0 이후 확정: 항공사진 출처와 접근 방식(가장 큰 리스크), 지도·로드뷰 제공자(13절), 근접 연도 허용 범위(제품 정의서 6.1절 초안 ±5년), 상업 이용 여부(13절), 동네 곳곳 사진의 출처.

### M5 도시의 대표 풍경 — 3개로 나눈다
- M5a `feat/landmark-data` (content-curator + backend-dev): `data/landmarks/` 대표 명소와 스키마, 존재 기간(`existed_from`/`existed_until`), 스키마 검증 테스트(backend-dev). 데이터 작업만이라 M2a 이후 M3·M4와 병렬로 진행할 수 있다.
- M5b `feat/landmark-media` (content-curator): `data/media/` 명소별 기록 사진·영상(6.2절 필드 전부, 라이선스 미확인은 `link_only`).
- M5c `feat/city-section` (backend-dev + frontend-dev): 출생 연도에 존재한 명소만 고르고 가장 가까운 연도의 미디어를 붙이는 API와 도시 섹션 UI.
- 완료 기준 요약: 1988 서울 결과에 그해 존재한 명소 5~8곳이 정밀도 표기와 함께 나오고, 그때 없던 명소는 빠진다.
- M0 이후 확정: 기록 미디어 출처, 상업 이용 여부(13절, 쓸 수 있는 공공누리 유형), 영상 처리 방식(13절), 지원 시작 연도(13절, 명소의 시대 분포 기준).
- M5 계획 때 PM이 정할 것: MVP에서 큐레이션할 시·도 범위(추천: 데모에 필요한 서울·광주부터).

### M6 이야기 화면 완성 — 3개로 나눈다
- M6a `feat/story-flow` (frontend-dev): 오프닝 → 동네 → 도시 → 세계 → 마무리 흐름, 섹션별 지연 로딩, `tragic` 사건의 차분한 분리, "다시 해보기".
- M6b `feat/sources-and-resilience` (backend-dev + frontend-dev + test-engineer): 결과 전체 출처 목록, 외부 출처 하나를 끊었을 때 해당 섹션만 비는지, 오프닝 3초·전체 10초 측정.
- M6c `chore/demo-e2e` (test-engineer + PM): 데모 입력 3개 Playwright E2E(목 서버 사용), 실행 방법 문서, 배포를 결정했다면 배포 설정.
- 완료 기준 요약: 제품 정의서 12절 완료 조건 3개(세 입력 모두 끝까지 결과, 모든 미디어에 출처·라이선스·촬영 시점·정밀도, 외부 출처 하나를 끊어도 화면 유지)를 E2E 테스트로 확인.
- M0 이후 확정: 배포 여부와 대상(13절). 공개 배포면 지도 SDK 도메인 등록, 출처별 상업·공개 이용 조건을 다시 확인한다.

## 순서를 이렇게 정한 이유

1. **M0가 맨 앞**: 이 서비스는 "쓸 수 있는 사진과 영상이 있는가"에 성패가 달려 있다. 출처와 약관을 확인하기 전에 코드를 쓰면 버릴 가능성이 크다.
2. **M2가 모든 섹션보다 먼저**: 동네·도시 섹션은 모두 좌표와 장소 유형이 있어야 동작하고, 오프닝과 결과 화면 뼈대가 이후 섹션이 붙을 자리다.
3. **M3를 M4·M5보다 먼저**: 사건 데이터는 위치와 상관없어 데모 입력 3개 모두에 바로 결과를 낼 수 있고, 키 없는 공개 API일 가능성이 높아(M0에서 확인) 외부 리스크가 가장 작다. 또 공용 미디어 형식, `date_precision` 계산, 미디어 카드, `link_only` 렌더링을 여기서 만들면 M4·M5가 재사용한다.
4. **M4를 M5보다 먼저**: 동네 섹션이 목표 감정("우리 동네가 이랬구나")의 핵심이고 리스크도 가장 크다(항공사진). 문제가 있으면 일찍 드러나야 범위를 조정할 시간이 있다.
5. **M5a는 병렬 가능**: 큐레이션 데이터는 `data/` 만 건드리므로 M2a(지역 코드) 이후 M3·M4와 병렬로 content-curator가 진행할 수 있다. 오케스트레이터가 worktree 격리로 돌린다.
6. **M6는 마지막**: 흐름과 성능은 섹션이 다 있어야 다듬을 수 있다.

## 가장 큰 리스크 3가지와 대응

1. **과거 항공사진을 좌표·연도로 프로그램에서 받을 수 없을 수 있다** (웹 열람만 가능, 신청·유료 다운로드, 정사보정이 안 돼 현재 위성과 겹치지 않음).
   - 대응: M0 T2에서 접근 방식, 정사영상 여부, 연도 커버리지를 최우선으로 확인한다. 안 되면 (a) 데모 지점만 라이선스가 허용하는 범위에서 미리 골라 둔 데이터로 대체, (b) 슬라이더 대신 "그때 사진 링크 + 현재 위성" 구성으로 축소 중 하나를 M4 계획 때 PM이 고른다.
2. **기록 사진 대부분이 공공누리 2~4유형이거나 라이선스 표시가 없어 `link_only` 비율이 높아질 수 있다.** 상업 이용을 택하면 더 줄어든다.
   - 대응: M0 T4에서 상업·비상업 두 시나리오별로 쓸 수 있는 자료 비율을 샘플로 추정하고, 13절 상업 이용 결정을 M0 직후에 받는다. Wikimedia Commons의 PD·CC 자료와 명소별 큐레이션(M5b)으로 `embed` 가능한 자료를 미리 확보한다.
3. **그날의 사건이 정확한 날짜가 아니거나 한국어 데이터가 적고, `tone` 을 잘못 판정하면 생일 분위기에 참사가 섞인다.**
   - 대응: M0 T5에서 데모 날짜 3개로 연·월·일 정확도와 한국어 데이터 양을 실제 응답으로 확인하고, `tone` 판정 방식 후보(규칙/큐레이션 목록/혼합)를 비교한다. M3a에서는 판정이 불확실한 사건을 `tragic` 쪽으로 분류하는 보수적 기본값을 계획서에 둔다.

## ★ PM 직접 구현 후보 (각 계획서에서 하나씩 확정)

- M1a: Flyway 기준 마이그레이션과 JPA 설정
- M2a: 장소 해석 결과 캐시 엔티티와 캐시 전략(약관이 허용하는 범위)
- M3a: 미디어 선택과 `date_precision` 계산 도메인 로직
- M4a: 항공사진 근접 연도 선택과 외부 호출 타임아웃·장애 격리
