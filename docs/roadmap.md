## M0 결과로 바뀐 점 (요약)

summary 7.2절을 반영했다. 자세한 내용은 각 마일스톤 상세에 있다.

1. **M2a**: 장소 검색 1순위(카카오 로컬)가 아직 `부분 확인 (PM 호출 대기)` 다. "약관이 허용하면 캐시"는 **지역 사전 + 실시간 호출**로 줄어들고(#11 추천 (a)), ★ 후보 "장소 해석 결과 캐시 엔티티"는 바꾼다.
2. **M3는 M1 직후 시작한다** (R1 (a) 결정): 그날의 사건 1순위(한국어 위키백과·Wikidata·Commons)는 모두 `확인됨` 이고 키가 필요 없다(User-Agent만).
3. **M4a**: 과거 항공사진 API가 없고 2010년 이전 촬영분은 정사영상이 아니다. "항공사진 어댑터"는 큐레이션 데이터(PM 신청 + content-curator 기록)를 읽는 것이 되고, "비교 슬라이더"는 **나란히 보기**로 바뀐다. 과거 쪽은 #9 답이 오기 전까지 `link_only`.
4. **M4b**: 로드뷰는 현재 모습만 가능하다. 카카오는 촬영 시점을 주지 않으므로 "현재 모습(촬영 시점 미제공)"으로 표기한다(#17). 로드뷰 유무는 서버에서 미리 알 수 없어 화면이 "로드뷰 없음"으로 바뀌는 흐름이 필요하다.
5. **M4c**: 서울은 "사진으로 본 서울" 큐레이션, 서울 밖은 Commons 현재 모습과 정직한 안내. **담당에 content-curator 추가.**
6. **M5**: 서울 명소는 서울역사아카이브(1957~1988)와 사진으로 본 서울(1995~)로 채우고 **1989~1994년은 공백**이다. **광주는 제1유형 기록 사진 원천이 없다.**
7. **M3c**: 날짜로 자동 조회할 국내 출처가 없어 **MVP 제외 추천**(#24). 아직 PM 미결정.
8. **테스트 fixture**(#12 결정, `CLAUDE.md` 7절 5항 반영): 카카오·네이버·Google 응답과 지도 화면은 공식 문서 필드 구조로 만든 **합성 fixture와 SDK 스텁**. Wikimedia 응답은 녹화 fixture 가능. 아래 마일스톤의 "녹화한 fixture" 표현을 이에 맞게 고쳤다.

## 마일스톤 상세

### M0 데이터 출처 리서치 — `docs/m0-source-research` (완료)
- 결과: 영역 문서 5개(`docs/research/place-search.md`, `aerial-imagery.md`, `satellite-streetview.md`, `archive-media.md`, `day-events.md`)와 `docs/research/summary.md`. 결정 26개(summary 6절).
- `확인됨` 1순위: 그날의 사건(한국어 위키백과, Wikidata, Commons), 서울 기록 사진(서울역사아카이브, 사진으로 본 서울), Commons 위치 기반 검색.
- 아직 못 쓰는 1순위: 카카오 로컬(M2a), 국토정보플랫폼 항공사진(M4a), 카카오맵 Web API(M4a·M4b). 올리는 방법은 summary 2.2절.
- 계획서: `docs/plans/m0-source-research.md`

### M1 부트스트랩 — 2개로 나눈다 (병렬)
- 나누는 이유: Gradle·Spring·Docker Compose·Flyway·CI와 Vite·React·테스트 도구 설정을 합치면 400줄을 넘을 가능성이 크고, 폴더도 `server/` 와 `web/` 로 깨끗이 나뉜다.
- M1a `chore/bootstrap-server` (backend-dev): `server/` Gradle 프로젝트(Spring Boot 4.1.x), Docker Compose PostgreSQL, Flyway 기준 마이그레이션, `GET /api/health`, Testcontainers 스모크 테스트, `.env.example`, `server-ci.yml`. 계획서 `docs/plans/m1a-bootstrap-server.md`.
- M1b `chore/bootstrap-web` (frontend-dev): `web/` Vite + React + TypeScript, Vitest·Testing Library·MSW, ESLint·Prettier, 입력 화면 자리와 빈 결과 화면(섹션 자리 5개), `/api` 개발 서버 프록시, `web-ci.yml`. 계획서 `docs/plans/m1b-bootstrap-web.md`.
- 확정된 것: 기술 스택은 `CLAUDE.md` 0절 초안대로(#6), Spring Boot는 4.1.x(M1a P1). CI는 테스트·린트만, 배포 잡 없음(#5). 좌표 변환 라이브러리는 1순위 조합(카카오)에서는 필요 없다. 지도 SDK 로더는 M4로 미룬다. summary 8절 항목별 처리는 M1a 계획서에 있다. M1a·M1b는 worktree 병렬로 진행하고 파일 단위 소유 예외를 승인받았다(M1a P4).

### M3 그날의 세계 — 2개 + 조건부 1개 (M1 바로 다음)
- 나누는 이유: 사건 어댑터·위키텍스트 파서·정확한 날짜 필터·Commons 라이선스 판정·`tone` 판정(백엔드)과 섹션 UI·미디어 캡션·`link_only` 렌더링(프론트엔드)을 합치면 400줄을 넘는다. M3a가 계획 단계에서 400줄을 넘을 것 같으면 "위키백과 날짜 문서 어댑터·파서"와 "미디어·`tone`"으로 다시 나눈다.
- M3a `feat/world-events-api` (backend-dev, `tone` 데모 날짜 큐레이션은 content-curator)
  - 출처: 한국어 위키백과 날짜·연도 문서(Action API) + Wikidata + Commons (#20 추천 (a)). On this day는 필수 의존으로 두지 않는다.
  - 범위: 위키텍스트 파서("사건"·"문화" 절만, `revid` 저장), 같은 연·월·일 필터, 미디어 레코드(6.2절 필드 전부)와 `date_precision` 계산, Commons 비자유 이미지 거르기(`imagerepository`, `NonFree`, 허용 라이선스 목록), `display_mode` 결정, `tone`(#22 추천 (c), `tone_basis`), 빈 날짜 안내(#21). 여기서 **공용 미디어 형식**(`data/schema/media.schema.json` 과 API DTO)을 확정하고 #17·#18 결과를 넣는다. M4·M5가 재사용한다.
  - M2보다 먼저 하므로 이 기능이 첫 도메인 API다. 섹션별 엔드포인트 형태, 에러 응답 형식, 날짜 파라미터 검증(형식, 존재하는 날짜)을 M3a 계획서에서 정한다. 지원 시작 연도 등 입력 규칙 전체는 M2b가 맡는다.
  - 외부 호출 공통 설정을 여기서 처음 만든다: 어댑터별 타임아웃, `WIKIMEDIA_USER_AGENT` 헤더, 429·`Retry-After` 처리, 엔드포인트 설정값(Wikidata 백엔드 이전 대비). Wikimedia 응답은 녹화 fixture 가능(#12).
  - 위키백과 날짜·연도 문서는 라이선스상 캐시할 수 있다(summary 8절 6항). 캐시 테이블은 이 기능의 첫 도메인 마이그레이션 후보다.
  - Commons 사건 이미지의 사본 여부는 #13 (a)와 같은 방식으로 M3a 계획 때 정한다.
- M3b `feat/world-events-ui` (frontend-dev): 그날의 세계 섹션, `tragic` 사건 분리 표시, 공용 미디어 카드(출처·라이선스·촬영 시점·정밀도 표시, `link_only` 는 썸네일 없이 링크), 위키백과 문장의 CC BY-SA 4.0 표기와 문서 링크(#23).
  - 입력 화면이 아직 없으므로 M1b의 `world` 섹션 자리에 붙이고 컴포넌트 테스트(MSW)와 API 직접 호출(`curl`)로 확인한다. 입력부터 세계 섹션까지 이어지는 흐름은 M2b에서 연결한다.
- M3c `feat/domestic-events` (조건부): **MVP 제외 추천**(#24 (a)). 데모 3개 날짜에서 위키백과보다 더 주는 사건이 없었다. PM이 (b)를 고르면 대한뉴스 회차 링크 카드(1958~1994년, `link_only`, 근사 날짜)만 넣는다.
- 완료 기준 요약: 1988-09-17 결과에 서울 올림픽 개막이 나오고(제품 정의서 12절, 한국어 위키백과로 채울 수 있음), 1995-03-15처럼 사건이 비는 날은 #21 안내가 나오며, 라이선스가 확인되지 않은 미디어는 `link_only`, 모든 미디어에 정밀도 표기가 있다.

## 순서를 이렇게 정한 이유

1. **M0가 맨 앞** (완료): 쓸 수 있는 사진과 영상이 있는지에 성패가 달려 있어서 출처와 약관을 먼저 확인했다.
2. **M1 다음**: 모든 기능이 붙을 골격과 CI가 먼저 있어야 한다. M1a와 M1b는 폴더와 파일이 겹치지 않아 병렬로 진행한다(M1 계획서 "M1a·M1b 경계").
3. **M3를 M1 바로 다음에** (R1 (a)): 사건 데이터는 위치와 상관없고 출처가 모두 `확인됨` 이며 키가 필요 없다. 공용 미디어 형식, `date_precision` 계산, 미디어 카드, `link_only` 렌더링을 여기서 만들면 M4·M5가 재사용한다. M2를 막는 것은 전부 PM 작업(키 발급, 확인 명령, 결정)이라 그동안 M3를 진행한다.
4. **M2가 동네·도시 섹션보다 먼저**: 동네·도시 섹션은 좌표와 장소 유형이 있어야 동작한다. 입력 → 오프닝 → 세계 섹션 흐름도 M2b에서 연결된다.
5. **M4를 M5보다 먼저**: 동네 섹션이 목표 감정의 핵심이고 리스크가 가장 크다. M0로 범위는 이미 줄었지만(나란히 보기, `link_only`), 카카오맵 Web API 확인과 #9 답이 일찍 드러나야 한다.
6. **M5a는 병렬 가능**: 큐레이션 데이터는 `data/` 만 건드리므로 M2a(지역 코드) 이후 M4와 병렬로 진행할 수 있다.
7. **M6는 마지막**: 흐름과 성능은 섹션이 다 있어야 다듬을 수 있다.

## 가장 큰 리스크 3가지와 대응

1. **장소·지도 1순위(카카오)가 아직 `확인됨` 이 아니다** — 카카오 로컬은 `부분 확인 (PM 호출 대기)`, 카카오맵 Web API(스카이뷰·로드뷰)는 커버리지 문서가 없어 `미확인`. M2와 M4가 모두 여기에 걸려 있다.
   - 대응: K1~K6·D1~D2와 브라우저 확인 13·15·K-S1을 PM 작업 목록 앞쪽에 둔다. 기다리는 동안 M3를 먼저 진행한다(R1). 카카오가 막히면 #2 (c) Google로 바꾸되, #7(다른 회사 지도와 같은 화면에 두기) 제약 때문에 M4a의 나란히 보기 설계를 다시 본다.
2. **동네·도시 섹션의 "그때"가 비어 있을 수 있다 (M0에서 현실이 됨)** — 과거 항공사진은 API가 없고 수작업 신청뿐이며 2010년 이전은 정사영상이 아니다. 제1유형 기록 사진은 서울에만 있고 서울도 1989~1994년이 공백이다. 제3·4유형은 #9 답 전까지 `link_only`.
   - 대응: #14 (c) 구성으로 "그때"가 없으면 현재 모습과 정직한 안내를 보여 준다(제품 정의서 6.1절). 데모 지점만 큐레이션한다. #9 서면 문의를 지금 보내 답을 M4 전까지 받는다. 빈 섹션 안내 문구는 M3b·M4·M5c에서 같은 컴포넌트로 만든다.
3. **그날의 사건이 비거나 `tone` 을 잘못 판정할 수 있다 (M0에서 확인됨)** — 1995-03-15는 공개 출처에서 국내 사건이 0건이고, 구조화 규칙은 비극 사건 8건 중 7건만 잡았다.
   - 대응: #21 (a) 빈 날짜 안내, #22 (c) 규칙 혼합 + 데모 날짜 큐레이션 덮어쓰기 + 불확실하면 `tragic`. M3a 완료 기준에 데모 날짜 3개의 `tone` 결과 검수를 넣는다.
